## Learned memory

Devin has persistent cross-session memory on its cloud surface, in several account-scoped forms. Knowledge (Settings > Resources > Knowledge) is a bank of tips, instructions, and documentation that Devin recalls automatically when a session's work matches an item's trigger description; items are scoped to repositories, organizations, or the enterprise, and can carry macros. Knowledge is deprecated and is being migrated automatically to skills in plugins, with skills the recommended replacement. Devin additionally auto-generates repository Knowledge from READMEs and file structure of connected repos, and auto-pulls and updates Knowledge from specialized repository files (.rules, .mdc, .cursorrules, .windsurf, CLAUDE.md, AGENTS.md). A second cloud mechanism is the Automations scratchpad: a persistent document shared by a monitor automation and its child sub-devins that accumulates context across runs and acts as the automation's long-term memory. Cloud sessions themselves persist server-side and can be resumed later (devin --cloud -r). On the local surface, the Devin CLI documents no separate agent-memory store; durable context lives in rule and skill files, and local sessions persist only as resumable conversations (devin --continue, devin -r). In Devin Desktop, the legacy Cascade agent stores auto-generated memories locally in ~/.codeium/windsurf/memories/ (workspace-scoped, machine-local, never committed), while the Devin Local agent — the default — does not persist memories, and the docs advise migrating relied-upon Cascade memories to skills. For cloud sessions, cross-session memory therefore lives in the Devin account (Knowledge, plugins/skills at personal, organization, or enterprise scope) rather than in the repository, except where skills are committed to the repo as files.

## Compatibility notes

Devin spans four documented surfaces: cloud sessions (app.devin.ai virtual machines), the Devin CLI in the terminal, Devin Desktop (which ships two agents — Devin Local, which is the Devin CLI harness, and the legacy Cascade agent), and Devin Review (cloud PR review). Convention-file support differs by surface and the atlas entries above mark each path accordingly. Cloud sessions load instruction context from repository AGENTS.md files (16 KiB per file, auto-injected) and discover skills from six directories scanned in every connected repository (.agents/skills, .devin/skills, .github/skills, .claude/skills, .cognition/skills, .windsurf/skills); indexed repos make skills available before cloning, and disk-scanned skills from a clone override matching indexed skills. Docs do not state that cloud sessions directly read CLAUDE.md, .devin/rules, .cursor/rules, or other local tool rule files — those reach the cloud only through Knowledge auto-pull (deprecated) and Devin Review's review-context list, so claims of direct cloud reading would be unsupported. The CLI is where the broad interop lives: it reads AGENTS.md, AGENTS.local.md, AGENT.md, .windsurfrules, and CLAUDE.md identically as always-on rules, native .devin/rules with trigger frontmatter, .devin/global_rules.md (which shadows .windsurf/global_rules.md), and it imports other tools' configuration by default under seven read_config_from keys (agents_standard, cursor, windsurf, claude, copilot, opencode, zed — all default true), covering Cursor rules and MCP, Windsurf rules/skills/MCP, Claude Code rules, skills, commands-as-skills, custom subagents and hooks, Copilot skills (read in place, since they use the same SKILL.md format), OpenCode MCP (with schema conversion), and Zed MCP (context_servers key). Plugin subagents and plugin hooks load only in local Devin agents (CLI and Devin Desktop), not in cloud sessions, and plugin hooks are documented as best-effort and fail-open. Two explicit exclusions are worth recording: Windsurf workflows (.windsurf/workflows/ and ~/.codeium/&lt;channel&gt;/global_workflows/) are not imported as skills, and GitHub Copilot custom instructions (.github/copilot-instructions.md and .github/instructions/*.instructions.md) are not imported. Cross-session instructions can also live outside files entirely in the cloud account: Knowledge items, Playbooks (reusable prompts that are cloud-only, not available in the CLI), and organization-defined slash commands that expand into predefined prompt templates — these are stored in Devin, not in the repository. Plugin-based instruction files (an always-on AGENTS.md at the plugin root plus rules/*.md with trigger frontmatter) are injected in every session where the plugin is installed, and plugin install authority ranks Enterprise manifest > Org manifest > repository .devin/config.json lists > user installs. For enterprise-managed local use, the CLI's system.json pins auth and proxy settings machine-wide at /etc/devin/system.json (Linux), /Library/Application Support/Devin/system.json (macOS), and C:\\ProgramData\\Devin\\system.json (Windows); no equivalent enterprise instruction-file mechanism for cloud sessions is documented. Where docs are silent, this atlas says so rather than guessing: no precedence order is stated among multiple competing always-on rule files (they are loaded together, with only .devin-vs-.windsurf global_rules.md shadowing documented), no finer path than "the .claude/ directory" is given for Claude Code custom-subagent import, and the ordering among Devin Review's default instruction files is unspecified.
