## Learned memory

Kiro documents two kinds of persistent agent memory. On Kiro Web, the agent keeps an automatic account-level memory: as you work and give feedback — including guidance left on pull-request reviews — it learns preferences and applies them to future work across all repositories. That memory is maintained automatically, surfaced in the Settings > Memory section of Kiro Web, can include or exclude individual learned items, and is explicitly documented for Kiro Web (cloud sessions) rather than the local surfaces. For the IDE and CLI, no separate automatic memory is documented; the persistent-context mechanism there is explicit steering files on disk, which survive across sessions by design. Separately, the open-source Kiro Crew agent ships a six-layer memory rooted at ~/.kiro/crew/workspace/memory/: preferences.md (replaced wholesale by a consolidator every 30 messages, injected into every new session), projects.md, recent history under history/*.md with a three-tier decay, SQLite-backed semantic memory (confidence-gated writes) and episodic memory tables with an optional FAISS index plus time-decay and MMR reranking, and a lessons layer where learned corrections override defaults and user-explicit lessons always win.

[src](https://kiro.dev/docs/web/memory/)

## Compatibility notes

All file paths above were read from pages on kiro.dev/docs fetched during this documentation pass; each canonical page also has a markdown twin at the same URL plus .md.

Compatibility with other harnesses: Kiro's docs document support for the AGENTS.md standard and the open Agent Skills standard, and say skills can be imported from the community or other compatible AI tools — the documented mechanism imports (copies) skill packages, it does not read foreign convention directories such as .cursor/rules, .cursor/skills, or .claude/skills in place; any direct reading of those paths is not documented. CLAUDE.md support is not documented. "Import" behavior places skills under .kiro/skills/ or ~/.kiro/skills/.

Cloud vs local surfaces: Kiro is not a cloud-only agent. One agent harness runs locally on IDE and CLI and in a managed cloud sandbox for Web, Mobile, and cloud sessions created from the IDE or CLI. Cloud sessions read project configuration committed under .kiro/ in the cloned repository (steering, specs, custom agents, hooks, MCP servers, and skills) and never the local ~/.kiro directory; personal configuration reaches the cloud only through Settings > Sync, and the cloud copy can optionally be applied to new local sessions. Kiro Mobile reads project steering and skills only and uses built-in agents. Kiro Web additionally reads project MCP servers, custom agents, and hooks, and can invoke project agents as sub-agents but not as the primary session agent.

Precedence summary across scopes: steering, skills, and hooks merge across all scopes (workspace steering wins conflicts, and workspace skills take priority over same-named global skills); custom agents resolve project > global with same-name project winning; MCP servers resolve agent config > workspace mcp.json > global mcp.json; workflow recipes resolve project > global > synchronized account recipes > bundled recipes; permissions use deny-overrides with enterprise managed-settings.json outranking user rules; managed settings are client-enforced on the machine and do not apply to Kiro Web.

Additional documented paths and controls: the KIRO_HOME environment variable redirects the global ~/.kiro directory (agents, skills, steering, settings, and sessions all resolve against it). CLI settings live at ~/.kiro/settings/cli.json (global only). Agent-scope MCP, permissions, hooks, powers, steering, and skills are embedded in the agent configuration file rather than separate paths. Kiro IDE extension registry and MDM extension controls exist for VSIX tooling but no instruction content is documented in them.
